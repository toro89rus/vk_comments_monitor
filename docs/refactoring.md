# План рефакторинга

Здесь правки, которые не меняют поведение бота: тесты проходят до и после без изменений (кроме импортов
при переносе модулей). Баги и решения о поведении — в [issues.md](issues.md).

Шаги идут по порядку: каждый следующий опирается на предыдущие или становится проще после них. Один шаг —
один или несколько коммитов, каждый проходит `make check`. Сделанный шаг удаляется из файла в последнем
коммите шага. Номера оставшихся шагов не меняются: на них ссылаются другие записи.

Пометки:
- **согласовать** — шаг трогает файлы, которые по CLAUDE.md меняются только с согласия владельца
  (`pyproject.toml`, `uv.lock`, `Makefile`, `Dockerfile`, `docker-compose.yml`), или ждёт его решения;
- **ждёт Qn** — нужен ответ на вопрос из [issues.md](issues.md).

## Этап 1. Мёртвый код и мелочи

Самые дешёвые шаги. После них меньше кода переносить и переписывать на следующих этапах.

5. **Зависимости:** удалить `telegram`, заменить `dotenv` на `python-dotenv`. **Согласовать.**

## Этап 2. Конфиг

6. **Загрузка `.env` только в `load_config()`:** убрать `load_dotenv()` при импорте `tatd_bot/config/config.py`.
   Тогда тесты не прочитают случайный `.env`. Добавить тесты на `load_config()` с подменой окружения.
7. **Порт Redis — в конфиг:** `RedisConfig.port` из `REDIS_PORT` (по умолчанию 6379), `Repository`
   получает хост и порт. Тот же шаг: `Repository` принимает готовый клиент Redis, и в тестах не нужна
   подмена атрибута `r`.

## Этап 3. Структура

Только переносы и разбиение, логика не меняется. Тесты меняют лишь импорты.

8. **Убрать лишнюю вложенность в `tatd_bot/tg/`:** `services/services.py` → `services.py`, так же для
   `models`, `mappers`, `keyboards`, `filters`, `states`. По одному пакету на коммит (`move …`).
9. **Мониторинг — на уровень приложения:** `VkCommentsMonitorService` из `tg/services` в
   `tatd_bot/monitor.py`. Это оркестрация vk → tg, а не часть Telegram-слоя.
10. **Разделить `VkMessageService._make_message_entity`** на две функции, для комментария и для ответа.
11. **Разделить `Repository`** на хранилище tg (подписчики, заявки, `bot_user`) и vk (комментарии, кэш
    авторов). Ключи Redis не меняются, миграция не нужна.

## Этап 4. Async

Главная цель рефакторинга: пока идёт проход мониторинга (до 10 с на каждый запрос VK), бот не отвечает
пользователям. На этом этапе тесты затронутых модулей тоже станут async (`await` перед вызовами). Это
механическая правка: проверки (`assert`) не меняются.

12. **Клиент VK на `aiohttp`:** `VkApiService` и вызывающий его `VkFeedService` становятся async. Обработка
    ошибок пока остаётся прежней: пустой результат. **Ждёт Q4** — если решим обрабатывать ошибки иначе, это
    отдельный коммит с изменением поведения после этого шага. Удалить `requests`. **Согласовать** (зависимости).
13. **Redis на `redis.asyncio`:** оба хранилища и все сервисы и хендлеры над ними становятся async.
    `fakeredis` поддерживает async-клиент.

## Этап 5. Docker и окружение

Отдельно и в конце: эти шаги меняют то, что выкатывается на сервер. Проверка — локальная сборка
образа (`docker compose build`). Бота не запускать: боевые токены.

14. **Образ:** `uv sync --no-dev` для образа, зафиксированные версии `uv` и `redis`, опечатки в
    `.dockerignore` (`.ruff_cahe/`, `.gitignore/`). **Согласовать.**

## Вне плана

- **Деплой только зелёного `main`.** `main` защищён на GitHub: мерж только через PR с зелёным `check`.
  Остаётся вторая линия — проверка статуса CI в `deploy.sh` перед `git pull`, на случай если защиту
  обойдут или отключат. **Согласовать.**
- **Исправление багов из [issues.md](issues.md)** не входит в рефакторинг, но и не обязано ждать его конца.
  B2 («Комментарий от None») локальный, его можно исправить в любой момент. B1 (повторная рассылка)
  удобнее чинить после шага 9: рассылка тогда уже будет в своём модуле.
